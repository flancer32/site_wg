# Дата-объекты в JavaScript

Я программировал много на LotusScript, Java и PHP. Первый язык сейчас широко не употребляется, а во втором и третьем понятие “дата-объекта” занимает значимое место: [POJO](https://en.wikipedia.org/wiki/Plain_old_Java_object) и [stdClass](https://stackoverflow.com/questions/931407/what-is-stdclass-in-php). Что лично я подразумеваю под “дата-объектом”? Дата-объект — это чистые данные, без поведения. В нём есть только свойства-данные, свойства-методы отсутствуют.

## Дата-объект и JSON

В JS встроены преобразования любого JS-объекта в JSON и обратно:

const js = {a: 3, b: 'text', c: true};

const json = JSON.stringify(js); // {"a":3,"b":"text","c":true}
Если наш `js`-объект содержит свойство-функцию, то при преобразовании в JSON это свойство игнорируется:

const js = {

 name: 'data-object',

 method: function () {

 return this.name

 }

};

const name = js.method(); // 'data-object'

const json = JSON.stringify(js); // {"name":"data-object"}
Так вот, дата-объект может быть преобразован в JSON и обратно без потери данных. А так как JSON-преобразования доступны не только в JavaScript, но и в других языках, то дата-объекты могут без потерь передавать информацию между приложениями, написанными на различных языках программирования:

<?php

$obj = json_decode('{"a":3,"b":"text","c":true}');

echo var_dump($obj);class stdClass#1 (3) {

 public $a =>

 int(3)

 public $b =>

 string(4) "text"

 public $c =>

 bool(true)

}
Примерно так же можно передавать данные между приложениями при помощи XML и YAML.

В общем, дата-объекты представляют из себя структуры “чистых данных”, которые могут сохранятся в базах (реляционных и [NoSQL](https://ru.wikipedia.org/wiki/NoSQL)) и могут использоваться для передачи данных между различными приложениями.

## “Пчёлы” и “пыльца”

В своих приложениях я предпочитаю разделять все объекты на две большие группы:

*   дата-объекты: служат для передачи данных между частями приложения;
*   обработчики: содержат методы обработки данных;

Можно сравнить объекты-обработчики с пчёлами, а дата-объекты — с пыльцой, которую пчёлы переносят с цветка на цветок (между частями приложения и даже отдельными приложениями).

## Структуры данных в JavaScript

В данных самое интересное — это структура. Что связано с чем и как. Для описания структуры объекта в ES2015 (ES6) используется конструкция `class`:

class Customer {

 name;

 address;

 orders;

}
В силу особенностей типизации в JS (динамическая, слабая, неявная) больше о структуре данных средствами самого языка мы сказать не можем . Вообще JavaScript накладывает на программиста _меньше_ ограничений, чем тот же PHP, и **_гораздо меньше_** ограничений, чем Java. Поэтому на JS очень легко писать код в принципе, проще писать плохой код и сложнее писать код хороший. Для создания хорошего кода приходится использовать сторонние инструменты (например, [TypeScript](https://ru.wikipedia.org/wiki/TypeScript)). Лично я предпочитаю [JSDoc](https://jsdoc.app/):

class Address {...}

class Order {...}class Customer {

 /** [@type](http://twitter.com/type) {String} */

 name;

 /** [@type](http://twitter.com/type) {Address} */

 address;

 /** [@type](http://twitter.com/type) {Order[]} */

 orders;

}
Примерно так можно было бы описать структуру данных о покупателе, содержащую подструктуру с адресом покупателя (страна, город, улица, дом) и список его заказов. Без JSDoc структуру данных средствами чисто JS описать не получится.

Но нужно понимать, что JSDoc — это прежде всего документация. Т.е., обращение разработчика к самому себе в будущем, к другим разработчикам и к средствам разработки (к IDE). Аннотации не влияют на выполнение кода интерпретатором.

## Мета-данные в дата-объекте

Зачастую данные для дата-объекта собираются различными частями приложения. Например, из различных источников данных (разных таблиц в одной базе данных, разных баз, внешних приложений):

/**

 * [@param](http://twitter.com/param) {Function} knex

 * [@returns](http://twitter.com/returns) {Promise<Customer>}

 */

async function getCustomer(knex) {

 const rs = await knex.from('customer')

 .select(knex.raw('CONCAT(first_name, \' \', last_name) as "name"'))

 .where('id', 8);

 const [first] = rs;

 return Object.assign(new Customer(), first)

}
Здесь свойство `Customer.name` собирается из двух столбцов (`first_name` и `last_name`) таблицы `customer` в базе данных.

Что плохого в данном коде? Как минимум то, что связь между свойством `name` и SQL выражением для выборки данных для этого свойства неявная. Если мы решим переименовать свойство `name`, то у IDE нет возможности помочь нам проверить, что это свойство используется в SQL выражении.

В ES2015 вместе с классами появилась возможность использовать статические члены в описаниях структур, поэтому можно переписать наш класс так:

class Customer {

 static NAME = 'name';/** [@type](http://twitter.com/type) {String} */

 name;

 ...

}
а код для выборки данных так:

knex.raw(`CONCAT(first_name, \' \', last_name) as "${Customer.NAME}"`)
В этом случае у IDE (и у программиста тоже — обычный текстовый поиск по исходникам) есть возможность определить, где использует свойство `name` или метаданные, соответствующие этому свойству.

## Резюме

Классы в JavaScript для описания дата-объектов (представление структуры данных без поведения) создаются с использованием возможностей ES2015, JSDoc и метапрограммирования (добавления в программу информации о самой себе):

class Customer {

 // metadata

 static ADDRESS = 'address';

 static NAME = 'name';

 static ORDERS= 'orders'; // attributes

 /** [@type](http://twitter.com/type) {Address} */

 address;

 /** [@type](http://twitter.com/type) {String} */

 name;

 /** [@type](http://twitter.com/type) {Order[]} */

 orders;

}
