# Имена ключей в БД

## Имена ключей в БД

Вчера мой сын спросил меня, каких правил я придерживаюсь в наименовании внешних ключей при разработке структур в базах данных. Я ответил, что:

FK_ИМЯ_ТЕКУЩЕЙ_ТАБЛИЦЫ_ИМЯ_СВЯЗЫВАЕМОГО_СТОЛБЦА
Т.е., для двух таблиц `customer` и `sale`:

CREATE TABLE customer (

 id ...

 PRIMARY KEY (id)

);
CREATE TABLE sale (

 id ...

 customer_ref ...

 PRIMARY KEY (id)

);

Мой ключ выглядел бы как:

FK_SALE_CUSTOMER_REF
На самом деле эту работу за меня последние несколько лет делал фреймворк (Magento, который сам внутри использует Zend) и его результат выглядел бы так:

FK_SALE_CUSTOMER_REF_CUSTOMER_ID
Принцип наименования, используемый фреймворком, [описан](https://stackoverflow.com/a/6954086/4073821) на StackOverflow:

FK_[THIS TABLE]_[THIS FIELD]_[THAT TABLE]_[THAT FIELD]
Этот принцип подходит только для простых внешних ключей, где задействовано только одно поле/колонка, но таких ключей, как правило, большинство в базе и именно они обеспечивают целостность данных.

Да, именно такой подход в наименоваии я рекомендую использовать при создании внешних ключей вручную. Почему?

Во-первых, все ключи (первичные, уникальные, внешние) для всех таблиц находятся в общем пространстве имён для отдельной базы. Поэтому для каждого типа ключа нужно вводить свой префикс или суффикс (я предпочитаю префикс):

*   **PK_**
*   **UQ_**
*   **FK_**

Во-вторых, естественная классификация объектов происходит от более общего класса к менее общему: год, месяц, день, час, … или страна, город, улица, … В этом случае сортировка записей по имени автоматом группирует объекты естественным образом:

*   20190104
*   20190623
*   20191231
*   20200101

(_попробуйте сделать то же самое с европейским (DD/MM/YYYY) или американским форматом (MM/DD/YYYY)_)

В базе данных самым крупным объектом является таблица. Использование на второй позиции имени таблицы, для которой задаются ключи, позволяют группировать естественным образом все ключи по типу и по таблице. Что может быть полезным, например, при работе с базами через десктопные клиенты типа [DBeaver](https://dbeaver.io/) (у них есть возможность просматривать все индексы в отдельном представлении). Как вариант, можно поменять имя таблицы и префикс местами, если группировка по имени таблицы предпочтительнее группировки по типу ключа (сам я предпочитаю первый вариант):

[THIS TABLE]_[PK|UQ|FK]_[...]
На уровне таблицы самым крупным объектом является поле/столбец. Логично, что мы используем имя столбца в формировании имени ключа, в котором этот столбец участвует (т.к. одна таблица может иметь различные внешние ключи по различным полям).

FK_[THIS TABLE]_[THIS FIELD]_...
Я придерживаюсь мнения, что идентификаторы сущностей должны быть примитивными (unsigned int), а не составными (составными могут быть идентификаторы в таблицах отношений между сущностями). Поэтому в моих таблицах идентификаторы сущностей называются просто `id` :

customer.id

sale.id
а поля, которые содержат ссылки на другие сущности имеют суффикс `_ref` :

sale.customer_ref
Для простых внешних ключей вполне достаточно добавить в имя название “_той_” таблицы, чтобы обеспечить уникальность имён по всей базе:

FK_[THIS TABLE]_[THIS FIELD]_[THAT TABLE]

FK_SALE_CUSTOMER_REF_CUSTOMER
А в случаях небольшого кол-ва таблиц в базе можно обойтись даже без имени “_той_” таблицы, т.к. стобцы внутри “_этой_” таблицы уже обеспечивают уникальность имени внешнего ключа в связке с именем таблицы:

FK_SALE_CUSTOMER_REF
Для собственного использования этого может быть более, чем достаточно, но если структура данных создаётся распределённо, различными командами разработчиков, через плагины (как это делается в Magento), то крайне рекомендую использовать полноформатное наименование для ключей с разделителями между таблицами и колонками:

FK_[THIS TABLE]__[THIS FIELD]__[THAT TABLE]__[THAT FIELD]
В таком названии ключа содержится достаточно информации, чтобы определить причину сбоя в случае ошибки:

The INSERT statement conflicted with the FOREIGN KEY constraint "FK_SALE__CUSTOMER_REF__CUSTOMER__ID".
Хотя `FK_SALE__CUSTOMER_REF` тоже вполне достаточно для собственного использования (если известно, что в базе есть только примитивные внешние ключи).

Если ключ составной (из нескольких колонок), то имя ключа может состоять из всех идентификаторов (имя таблицы и колонок) исходной таблицы (S — source) и конечной таблицы (T — target). В больших базах подчёркивание (“_”) обычно используется для визуального разделения частей в именах таблицы и колонок, поэтому двойное подчёркивание будет визуально разделять части ключа:

FK_[S_TBL]__[S_FLD1]_[S_FLD2]__[T_TBL]__[T_FLD1]_[T_FLD2]
Например в таблице `user_id_addr` колонки `user_ref` и `email_ref` ссылаются на таблицу `user` и колонки `id` и `email`:

FK_user_id_addr__user_ref_email_ref__user__id_email
Данный подход может сбойнуть, если в одной таблице есть колонки типа `user`, `ref`, `user_ref` и несколько ключей на внешние таблицы. Теоретически может возникнуть ситуация, когда из `user_ref` будет непонятно, это одно поле или два, но тут может помочь вторая часть имени (с конечной таблицей).

Это резюме моего собственного опыта на данный момент, с учётом, что я в основном работал с MySQL/PostgreSQL.
