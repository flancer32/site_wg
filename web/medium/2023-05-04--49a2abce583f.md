# Rational Web Development is Abnormal

As a web developer with over 20 years of experience in industries ranging from banking to e-commerce, I’ve used a variety of programming languages such as LotusScript, C, Java, and PHP. For the past three years, I’ve been developing web applications in JavaScript, and to my surprise, I’ve found that some of the most rational solutions from my point of view are unacceptable in modern web development for one reason or another. In this post, I’ll describe three points that have stood out to me in my recent experiences developing web applications.

## One Language for Both Ends

Despite the advent of NodeJS, which allows developers to use JavaScript for both frontend and backend web development, many web applications are still created using different languages for each end. While PHP, Ruby, Python, Java, and Go are still widely used for backend development, it seems obvious that a web application has the same subject area on both the frontend and backend.

It’s easier to describe the same entities and their logic for use in one language rather than in different languages. Using the same programming language for both ends can simplify the development process and make it easier to maintain and scale the application. However, despite the rationality of using a single language, it’s surprising how many job listings on Upwork require knowledge of both Laravel (PHP) and React (JS).

## The Discrepancy Between Development and Production Code

In the world of HTML editors, “What You See Is What You Get” (WYSIWYG) was once a popular expression that captured the idea of seeing the final result of your work immediately, without any additional transformations. However, in modern web development, it’s become normal to use transpilers, which convert the code that developers write into code that can run in the browser. One example of this is TypeScript.

I used GWT for over a year in my development work, writing Java code that was then transpiled into JavaScript for the front end. However, debugging code that was transpiled in production mode was nearly impossible because it was a completely different code than the one I had created.

The same situation exists with TypeScript. Although it is much closer to JS than Java, the essence remains the same: the code that runs in the browser is different from the code the developer wrote.

In my opinion, the evolution of JS has gradually blurred the distinction between TS and JS, making it possible to use modern IDEs and JSDoc to control types in an application without the need to transpile code.

The same is true for CSS. While there used to be a strong distinction between CSS and preprocessors like SASS, CSS 3 has made the gap much smaller.

While it may be rational to avoid additional transpiling, in the current state of affairs, it is not considered normal. The browser executes code that is completely different from what developers see in their IDEs.

## Namespaces

It’s surprising that JavaScript still doesn’t have a native namespace feature. What the JS community calls a “namespace” is actually a “scope”. Namespaces are used for organizing code in large projects (see `package` in Java and `namespace` in PHP). They are more about source code addressing and source loading than about naming conflicts at runtime.

In PHP, namespaces were introduced in version 5.3, but their counterparts had been used before, as seen in Zend 1 namespaces such as `Zend_Application_Bootstrap`. Similarly, in ES6+, it’s possible to create namespaces with the `import` function. In fact, I created my own Zend1-like namespaces about 3 years ago when I seriously started programming in JS ([@teqfw/di](https://github.com/teqfw/di)). Namespaces and source autoloading make it easy to build [IoC containers](https://www.php-fig.org/psr/psr-11/), without which the development of large projects is now basically unthinkable.

It’s rational to use namespaces and dependency injection in development, but the JS community has yet to adopt a common solution for this.

## Conclusion

It’s unfortunate that in modern web development, some rational solutions are not widely adopted due to the heavy legacy of corporations investing in certain technologies and developers investing their time in learning them. However, I remain confident that rationality will eventually become the norm. In the meantime, I will continue to develop web applications in pure JS (both for the backend, frontend, and shared code), without using transpilation and with utilizing namespaces and DI containers (like “[@teqfw/web](https://github.com/teqfw/web)”, for example).
