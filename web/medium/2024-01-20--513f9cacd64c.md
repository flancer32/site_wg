# Code Types in TeqFW: Defaults

In the “Code Types in TeqFW” series, I explore typical code elements that I use in my web applications. These articles are primarily intended to formalize my own development approach but may prove useful to other web developers. This post is dedicated to _hard-coded constants_.

“[Tequila Framework](https://flancer32.com/what-is-teqfw-45da7071fdd4)” is my personal way of building web applications using plain JavaScript, where the same JS code can be used without additional transpilation on both the backend and the frontend ([@teqfw/di](https://github.com/teqfw/di)).

## Simple Usage

Often in a project, there is a need to use _hard-coded constants_ at the level of a specific `npm` package. In such cases, I create a separate ES6 module `defaults.mjs` with content similar to the following:

export const DEF = {

 NAME: 'Main Defaults',

};
Using constants in the project:

import {DEF} from './defaults.mjs';

console.log(DEF.NAME);
## Dependencies

I adhere to the modular monolith architecture, so my web applications are built from individual `npm` packages. In this approach, it is often necessary to reference constants from one `npm` package to another. Instead of static imports, I prefer dependency injection through the constructor. If I want one set of constants to somehow reference another set of constants, I rewrite the code approximately as follows:

export default class Defaults {

 

 DEP1;

 

 DEP2;

 

 NAME = 'Main Defaults';
constructor(dep1, dep2) {

 this.DEP1 = dep1;

 this.DEP2 = dep2;

 Object.freeze(this);

 }

};

I use `Object.freeze(this)` in the constructor to prevent changing the values of constants after creating the corresponding object.

The code for dependencies looks something like this:

export default class Dep1_Defaults {

 NAME = 'Dependency One';
constructor() {

 Object.freeze(this);

 }

};

export default class Dep2_Defaults {

 NAME = 'Dependency Two';

constructor() {

 Object.freeze(this);

 }

};

Caller code for manually composing all dependencies:

import Defaults from './Defaults.mjs';

import Defaults1 from './dep1/Defaults.mjs';

import Defaults2 from './dep2/Defaults.mjs';
const DEF = new Defaults(new Defaults1(), new Defaults2());

console.log(DEF);

console.log(DEF.DEP1.NAME);

Result:

Defaults {

 DEP1: Dep1_Defaults { NAME: 'Dependency One' },

 DEP2: Dep2_Defaults { NAME: 'Dependency Two' },

 NAME: 'Main Defaults'

}

## Three Types of Defaults

I divide my source code within the `./src/` directory in the `npm` package into three sub-directories:

*   `./Back/`: contains sources used only in the Node.js environment;
*   `./Front/`: contains sources used only in the browser environment;
*   `./Shared/`: contains sources used in both Node.js and browser environments;

Usually, constants in the `Back` and `Front` branches refer to constants in the `Shared` branch. Therefore, almost all my `npm` packages have three`./Defaults.mjs|js` files each:

*   `./src/Back/Defaults.js`
*   `./src/Front/Defaults.js`
*   `./src/Shared/Defaults.js`

Typical content of these files, taking into account naming conventions for using [@teqfw/di](https://github.com/teqfw/di):

export default class Vnd_Prj_Back_Defaults {

 

 SHARED;
constructor({Vnd_Prj_Shared_Defaults$}) {

 this.SHARED = Vnd _Prj_Shared_Defaults$;

 Object.freeze(this);

 }

}

export default class Vnd_Prj_Front_Defaults {

 

 SHARED;

constructor({Vnd_Prj_Shared_Defaults$}) {

 this.SHARED = Vnd _Prj_Shared_Defaults$;

 Object.freeze(this);

 }

}

export default class Vnd_Prj_Shared_Defaults {

 NAME = '@vendor/package';

constructor() {

 Object.freeze(this);

 }

}

## Conclusion

Using hard-coded constants in this form allows the creation of a hierarchical tree of constants from `npm` packages used in the application development. When adding a constant in a dependent `npm` package, it becomes accessible in the base application code through a chain of dependencies: `DEF.DEP1.NAME`.
