# The Functional Objects in JS

In my JavaScript applications, I utilize a code pattern that I’ve coined as the Functional Object. In contrast to DTOs, which lack behavior, Functional Objects contain no data. To instantiate any objects in my applications, I employ a dependency-injected object container. At some point, I realized that Functional Objects constitute a significant portion of my codebase. In this post, I’ll endeavor to formalize, primarily for myself, what a Functional Object is and the role it plays in an application.

## Pure Function

In programming, a [pure function](https://en.wikipedia.org/wiki/Pure_function) is a function that performs some operations on input data, producing a result, but does not have any side effects (i.e., it does not modify its own state or the state of external resources). For example, consider the addition function:

function sum(a, b) {

 return a + b;

}
So, in a Functional Object, each method is a pure function:

const fnObj = {

 divide(a, b) { return a / b;},

 multiply(a, b) { return a * b;},

 subtract(a, b) { return a - b;},

 sum(a, b) { return a + b;},

};
What are the benefits of pure functions? Well, at least that you need exactly one instance of the function for the entire application.

## Dependency Injection

Modern JS programs consist of separate files (ES modules). Module binding occurs either statically at the time of writing the program (via export/import) or dynamically at runtime (via object containers). I predominantly use the second option, injecting dependencies through constructors or factory functions:

class FunctionObj {

 #dep1;

 #dep2;
constructor(dep1, dep2) {

 this.#dep1 = dep1;

 this.#dep2 = dep2;

 }

method(a, b) {

 const c = this.#dep1(a, b);

 return this.#dep2(c, a);

 }

}

In the case of pure functions, we have to pass dependencies along with data each time we call the function:

function method(a, b, dep1, dep2) {...}
Injecting dependencies into the constructor of a Functional Object allows separating data arguments from function arguments and helps reduce method signatures. However, in this form, the Functional Object is no longer a “pure function” because it has internal state defined by its attributes (#dep1 and #dep2). But if dependencies dep1 and dep2 themselves are pure functions, then the behavior of such an object _after its creation_ will be no different from that of a pure function. That is, we still only need exactly one instance of the Functional Object for our application, just like in the case of pure functions.

## Hierarchy of Functional Objects

If we continue to develop the idea of injecting dependencies into Functional Objects in the form of other Functional Objects, we can eventually arrive at a hierarchical structure of objects in the form of a tree, where each node exists as a singleton during the application’s runtime. Each node receives its state (functional dependencies) at the time of its creation and then acts as a pure function — performing operations on input data, producing a result, and having no side effects.

To some extent, such a tree can be viewed as an analogy to an LLM (Large Language Model) or the neural network of the human brain.

![Image 2](img/5a9b23e00557/image-01.png)

Each Functional Object can be associated with an individual neuron (or node of an LLM), and constructing the entire hierarchy of Functional Objects is akin to training an LLM or forming the brain. After training an LLM, you can pose various questions to the model and receive different answers based on the same structure. Similarly, after forming the hierarchy of Functional Objects, you obtain different output data for different input data using the same structure.

## DTO and Functional Objects

In my applications, it is possible to clearly distinguish a type of code that describes data — [DTOs](https://flancer32.com/dto-in-javascript-3274a3063919). For this type of code, there may exist multiple instances of objects of the same class in the application (for example, a list of users):

class UserDto {

 email;

 isAuthenticated;

 name;

}
let admins = [];

If we continue the analogy with the human brain, DTOs can be likened to the electrochemical signals transmitted between neurons (Functional Objects).

Each Functional Object is capable of generating new DTOs and passing them for processing to other Functional Objects. The quantity and type of generated DTOs are determined by the input parameters for the corresponding method of the Functional Object.

class AuthenticationService {

 

 #userDto;
constructor(UserDto) {

 this.#userDto = UserDto;

 }

authenticate(email, name) {

 const res = new this.#userDto();

 res.email = email;

 res.isAuthenticated = true;

 res.name = name;

 return res;

 }

}

Thus, each application at the moment of its execution can be represented as a static hierarchy of Functional Objects, in which DTOs are created and moved along based on input data.

Functional Objects are “the flesh and bones” of the application, while DTOs are its “blood”.

## Boundary Objects

It’s clear that data cannot just travel through the application; it must be stored somewhere. Code objects that interact with external resources or internal resources that change their internal state, I call Boundary Objects. In this post, I don’t delve into them, but just mention that an application consists not only of DTOs and Functional Objects.

## Conclusion

Utilizing Functional Objects in an application offers the same benefits as using pure functions — such code is easier to test, read, and maintain because the behavior of Functional Objects is more predictable than that of classical objects that mutate their internal state.

When instantiating objects in the application using an object container, each Functional Object is created as a singleton. This fact is good in itself — do not multiply entities unnecessarily.

The separation of the application code into data (blood) and functions (flesh) allows, in my opinion, for the construction of more versatile modules/packages and, consequently, more complex applications.
